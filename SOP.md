### 2026-08-17 — Tier 2 (partial): Conftest/Rego policies

### 2026-08-17 — Tier 2/3: CI/CD compliance gate workflow
- Created `.github/workflows/terraform_scan.yml`, triggered on `pull_request` for paths `terraform/examples/**` and `terraform/policy/**`. Two jobs:
  - `detect-changed-examples`: diffs the PR against its base ref to find which `terraform/examples/<dir>` directories actually changed, so the gate only scans what the PR touches — not every example directory on every PR (which would make a compliant-only PR fail forever, since the deliberately-broken `insecure-aws/` example permanently lives in the repo). If the diff touches `terraform/policy/` instead, all example directories are scanned, since a policy change can affect every directory, not just one.
  - `compliance-check`: matrix job, one run per changed directory. Writes a CI-only `override.tf` with mock AWS credentials (`skip_credentials_validation`, `skip_requesting_account_id`) before `terraform init`/`plan` — deliberately never uses real AWS credentials, since every resource in both example directories is a fresh `create` with no data source that needs a live AWS API response, so a policy check never needs real cloud access. This override is generated at CI runtime only, not committed, so local plans (which do use real `dev` IAM credentials) are unaffected. Runs `terraform show -json` → installs Conftest 0.69.0 (Linux x86_64, matching `ubuntu-latest`) → `conftest test` against `terraform/policy/` → writes results to the GitHub Actions job summary (`$GITHUB_STEP_SUMMARY`) → exits with Conftest's real exit code (via `set -o pipefail`, since piping through `tee` would otherwise mask a failing exit code) so the check genuinely fails the PR, not just logs a warning.
- **Bug caught before the first real run:** the bucket-name variables in both example directories have no defaults (a deliberate guard against accidental local apply), which would make `terraform plan -input=false` fail outright in CI with no value supplied. Fixed by adding `ci.auto.tfvars` to each example directory with placeholder bucket names — Terraform auto-loads these, and an explicit `-var` flag (as used for local testing) still takes precedence over them, so this doesn't change any prior local behavior.
- Not yet done at time of writing: branch protection on `main` requiring this check hasn't been configured yet — exact required-check context names are being confirmed from a first real run before adding them, since GitHub's required-status-check API needs the literal context string (`Compliance Check (terraform/examples/...)` for a matrix job).

### 2026-08-17 — Tier 1: per-resource evidence pushed to ServiceNow via a new child table
- Resolved the evidence-schema question that had been left open since Tier 1 was first scoped: a **new child table**, `u_aws_config_evidence`, with a Reference field (`u_control_mapping`) back to the existing `u_aws_config_control_mapping` table — not a JSON blob field on the existing table (the approach a now-closed PR, `fix/push-resource-detail-to-servicenow`, had taken). Reasoning: resource-level evidence is relational data (many findings per rule per run), and a blob field would recreate the exact overwrite problem the README already flags about `u_status` — this way each run's finding is its own row, nothing is ever overwritten, and it's browsable natively as a related list instead of requiring JSON-parsing.
- `u_aws_config_evidence` fields: `u_control_mapping` (Reference → `u_aws_config_control_mapping`), `u_resource_type`, `u_resource_id`, `u_annotation`, `u_compliance_status`, `u_captured_at` (Date/Time).
- `grc_validation.py`: `get_all_control_statuses()` now also captures `Annotation` (AWS Config's own explanation of why a resource is non-compliant) and `ResultRecordedTime` from `get_compliance_details_by_config_rule`, previously discarded — only `resource_type`/`resource_id` were kept before. Timestamp is formatted `%Y-%m-%d %H:%M:%S`, not ISO 8601, to match what ServiceNow's Table API expects for a Date/Time field.
- `update_service_now()` now returns a `{rule_name: sys_id}` map (previously returned nothing) so the new `push_evidence()` can link evidence rows back to the correct parent record without a second round of querying ServiceNow.
- New `push_evidence()`: for every non-compliant rule, POSTs one row to `u_aws_config_evidence` per non-compliant resource — always an insert, never a PATCH, by design.
- `main.py` wired: `push_evidence()` called right after `update_service_now()`, using the sys_id map it returns.
- **Verified live:** first real run hit a `401 Unauthorized` from ServiceNow on every call ("User is not authenticated") — unrelated to this change, a stale/rotated credential in `.env`. Re-ran after the credential was fixed: all 7 rules updated in `u_aws_config_control_mapping` successfully, and `push_evidence()` inserted 4 evidence rows across the 3 currently non-compliant rules (`cloudtrail-all-read-s3-data-event-check` ×1, `iam-password-policy` ×1, `subnet-auto-assign-public-ip-disabled` ×2, one per non-compliant subnet) — all `201 Created`, no failures. Confirms the field names on `u_aws_config_evidence` are correct and the child-table design works end to end against the real instance.
- Still open, separate from the data path above: the Related List for `u_aws_config_evidence` wasn't appearing in the parent table's Configure → Related Lists picker even with the Reference field confirmed correctly typed — likely a scope or cache issue, not a data-model problem, and doesn't block writes (evidence rows are being created either way, just not yet visible as a related list on the parent form until this is resolved).

### 2026-08-17 — Tier 4 (partial): single-call remediation guidance via Claude
- Decided **not** to build Tier 4 as a multi-step tool-use agent for this case: every lookup it would need (control policy/standard, evidence, risk exposure) is fixed and knowable in advance for a given non-compliant rule, so there's no case-by-case decision an autonomous loop would actually be making. Python pre-fetches everything and makes one call. Reserved actual multi-step `tool_runner` agentic behavior for a narrower future case — investigating a Tier 4a remediation *failure*, where the right next lookup genuinely depends on what the first one finds.
- Resolved where "the policy/standard for this control" comes from — deliberately **not** ServiceNow's `sn_compliance_control` (would need a new reference field and isn't cleanly queryable today) and **not** a hardcoded Python mapping (would duplicate control metadata a second time, same problem already flagged on risk ranges). Instead, pulled directly from **AWS Config's own `describe_config_rules` API** — `Description` and `InputParameters` are the authoritative, already-configured statement of what the rule checks and its exact thresholds for this account. New `grc_validation.get_rule_definition(config_client, rule_name)`.
- New `agent/remediation.py`: `build_prompt()` assembles the rule definition + evidence (annotation, resource type/id) into one prompt. `get_remediation_guidance()` calls the Claude API (`claude-sonnet-5`) with a single **forced tool call** (`tool_choice` pinned to `submit_remediation_guidance`) so the response is reliable structured JSON (`standard_summary`, `gap_summary`, `remediation_steps`) instead of free text needing a parser — "tool use" here as a structured-output mechanism, not an autonomous multi-step loop.
- `agent/__init__.py` added (empty) so the module can run as `python3 -m agent.remediation` from the repo root — needed for `grc_validation` (at the project root) to be importable; running it as a bare script (`python3 agent/remediation.py`) fails since that puts `agent/` itself, not the repo root, on `sys.path`.
- **Bug caught on first real run:** `max_tokens=1024` was too low — the model's `standard_summary`/`gap_summary` text alone consumed the budget, truncating the tool call before `remediation_steps` was ever produced (`KeyError: 'remediation_steps'`). Fixed two ways: raised `max_tokens` to 2048, and added an explicit "2-3 sentences, not a full essay" instruction to the two summary fields' schema descriptions to curb verbosity at the source. Also added a `stop_reason == "max_tokens"` check that raises a clear error instead of a confusing `KeyError` if this recurs.
- **Verified live** against a real non-compliant rule (`cloudtrail-all-read-s3-data-event-check`): produced an accurate standard summary (grounded in the rule's actual AWS description, correctly referencing CIS/PCI-DSS/NIST framework alignment), an accurate gap summary specific to the account's actual finding, and 8 concrete, correctly-ordered remediation steps (including real AWS CLI commands). Not yet wired into `main.py` or writing anywhere in ServiceNow — output currently only prints to the terminal via the module's manual test harness, same pattern as `notify.py` before it was verified. Requires `ANTHROPIC_API_KEY` in `.env`, now set.

### 2026-08-17 — Tier 4 wired into the pipeline, gated on new-vs-still-failing
- Investigated attaching guidance directly to ServiceNow's `sn_grc_issue` (discovered along the way that Policy and Compliance Management already **auto-creates** an issue when a control indicator fails — a real, un-planned finding: `sn_grc_issue.item` traces back to the exact `sn_compliance_control` sys_id each indicator script hardcodes). Decided **not** to have Python find-and-patch that issue directly — the issue is created by ServiceNow's own indicator, on ServiceNow's own schedule, which runs *after* Python writes `u_status`; patching it synchronously from the same pipeline run would usually fail to find it yet (a race, not a bug). Landed instead on: Python writes guidance into `u_aws_config_evidence` (already reliably reachable, no timing dependency), and ServiceNow-side automation (a Business Rule/Flow on `sn_grc_issue`, not yet built, on the user's side) pulls guidance from there when it creates the issue. Keeps Python's role fully synchronous and self-contained; defers "attach to the issue" to ServiceNow's own native workflow, consistent with the standing Python-computes/ServiceNow-natively-workflows split.
- Mapped rule → CIS v8 control for `u_compliance_control` (a List/`glide_list` field on `u_aws_config_control_mapping`, not a plain Reference — `cloudtrail-all-read-s3-data-event-check` genuinely maps to *two* controls, `Log Sensitive Data Access` and `Collect Audit Logs`, a real many-to-many the original single-Reference design couldn't hold). Only 4 of the 7 rules have a matching `sn_compliance_control` record today (`root-account-mfa-enabled`, `iam-password-policy`, and the two for `cloudtrail-all-read-s3-data-event-check`); the other 4 rules have no control yet, out of scope for now.
- Added drift-gating so Claude isn't called on every run for every still-open finding: `update_service_now()` now captures each rule's `previous_status` (read right before it gets overwritten) and returns `{rule_name: {sys_id, previous_status}}`. `main.py` only calls Claude when `previous_status != NON_COMPLIANT` (a genuinely new failure, including first-ever-seen rules). For a rule that was already non-compliant last run, new `grc_validation.get_latest_evidence_guidance()` fetches the most recent evidence row's guidance and carries it forward into today's row instead — so every evidence row still has guidance attached, without repeated API cost for an unchanged finding.
- `push_evidence()` now takes the richer `rule_context` dict (not just a flat sys_id map) plus an optional `guidance_by_rule`, and includes `u_standard_summary`/`u_gap_summary`/`u_remediation_steps` in every resource row's payload for that rule. `agent/remediation.py` gained `format_remediation_steps()` to join the structured steps list into numbered text, since ServiceNow's string field has no native list concept.
- **Verified live, both branches:** first real run after wiring found all 3 currently-non-compliant rules had also been non-compliant on the *previous* run, so all 3 correctly went to the carry-forward path — and correctly found nothing to carry forward, since their most recent evidence rows predated the guidance fields. To actually exercise the new-failure path, manually `PATCH`ed `iam-password-policy`'s `u_status` to `COMPLIANT` (a reversible data write) to simulate "was compliant last run," then re-ran: only `iam-password-policy` triggered `"Generated new remediation guidance"`, the other two correctly stayed on carry-forward. Confirmed via direct query that the resulting evidence row has real, correct guidance in all three fields, while sibling rows stay blank. The re-run's own `update_service_now()` call already wrote the true `NON_COMPLIANT` status back from AWS Config, so no manual cleanup was needed after the test.

### 2026-08-17 — Tier 6: FAIR-informed inherent risk, scoped deliberately smaller than FAIR-CAM
- **Scope decision, made under a real 2-day deadline (presentation):** considered porting the full FAIR-CAM engine from a separate prior project (`VendorRiskAutomation` — control-composite residual risk, marginal-simulation recommendations, LLM-derived threat intel), decided against it. Full FAIR-CAM needs genuine rework (remapping 6 vendor-control categories onto 7 AWS Config rules, tuning residual-risk composites defensible enough to hold up under direct questioning) that's real risk on a tight clock. Landed on inherent-risk-only, explicitly labeled "FAIR-informed, not full FAIR-CAM" — same conclusion the original implementation plan reached months ago for unrelated reasons, arrived at twice independently.
- `risk/fair_model.py`: `calculate_inherent_risk_distribution()` ported directly from `vendor_risk_engine.py`'s Monte Carlo function — same math (triangular distributions via `random.triangular`, no new dependency, `numpy` not actually needed despite being added to `requirements.txt` back in Tier 0), same Open FAIR (FAIR-U) approach of sampling (min, likely, max) ranges 10,000 times rather than using a single point estimate.
- `RISK_INPUTS`: illustrative (min, likely, max) contact-frequency/probability-of-action/loss-magnitude ranges for the 3 rules that currently have a mapped `sn_compliance_control` (`root-account-mfa-enabled`, `iam-password-policy`, `cloudtrail-all-read-s3-data-event-check`) — reasoned from published industry breach-cost benchmarks, not this org's own loss history, stated as such directly in the generated `description` text rather than waiting to be asked.
- **Output format resolved after direct pushback on an earlier draft:** first suggested leading with a single headline dollar figure for exec readability; correctly pushed back on — a range is more honest and more FAIR-aligned than a point estimate, and `vendor_risk_engine.py` already established that convention. Landed on: median + 90%-confidence range in one sentence, paired immediately with the remediation-cost comparison, not a full P10/P50/P90 stats table.
- **`u_compliance_control` was still empty on all 3 rows** when this tier started — the sys_id resolution from a few messages earlier had been discussed but the actual `PATCH` never happened (got sidetracked into the Related List/SigV4 detour). Populated it live before building the risk push. Also confirmed the field is still type `reference`, not `glide_list` as intended earlier — the List-type change never actually landed in ServiceNow. Known simplification, not fixed: `cloudtrail-all-read-s3-data-event-check` (which genuinely maps to two controls) only ends up linked to the first one (`Log Sensitive Data Access`), not both.
- Created 3 `sn_risk_definition` (Risk Statement) records via direct `POST` — ordinary business-record writes, not schema changes, same category already established as fine to do via API without asking each time. Confirmed first that `statement` isn't a mandatory field on `sn_risk_risk`, so this was a deliberate quality choice (use the platform's Risk Register as intended), not a hard requirement.
